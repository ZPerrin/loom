# Handoff: finish the 0.2 data plane and opening context

Discussion brief for the next Claude session. Recommendations below are proposals, not an
approved implementation. This file uses `kind: reference` because `handoff` is not yet accepted
by this repo's configured vocabulary. Reclassify it when that support lands.

## Objective

Make loom useful for the operator's coming month of work: codify handoffs and reports, then
give an agent a small, accurate description of the repo's loom tools and optional orientation.
An orchestrator should be able to equip a delegate deliberately, regardless of whether the
host starts a fresh session, forks history, or creates a subagent. Begin by reviewing this
direction with the operator; do not turn it into a general orchestration framework.

## Scope

In: the remaining data-plane work and a small revision of opening context. The operator wants
configurable repository bearings, a concise tool preamble, and efficient access to task state.
Loom has one active user; prefer a reversible design that can be evaluated through real use.

The [0.2 plan, item 8](../plans/2026-08-30-0.2.0-living-specs.md) already calls for handoff and
report kinds and examples. It separately calls for reviewing warp's required configuration
against harness-created workspaces. Item 9 still names the skill-authoring meta-reference.
Ask whether those latter items remain release requirements; this brief does not silently
remove them or make a full startup redesign another prerequisite. The [roadmap's Ideas](../../docs/roadmap.md)
already defers delegate markers, dispatch scripts, and automatic task-specific startup to 0.3.

### Recommended 0.2 shape

1. **Codify the files.** Add default `handoff` and `report` kinds, dated names, and optional
   `[handoffs].dir` / `[reports].dir`, following the existing relative-path convention. Update
   this repo's explicit kind list too. Use Objective, Scope, Constraints, Acceptance, Return
   for handoffs, distilled from [warp's delegation opinion](../skills/warp.md). Reports carry
   outcome, evidence, files/commits, and unresolved questions; start with examples rather than
   a new report grammar. A research handoff may leave decisions open for the operator; an
   implementation delegate's handoff settles the decisions its work depends on.
2. **Keep task state separate from repository orientation.** A startup section explains the
   project's current shape or operator preferences; the dispatched handoff supplies the task.
   Keep `slice_headers` and provenance. The operator can choose a short `## Orientation`
   section and a smaller commit count. Do not globally replace the existing `## Now` default
   without an explicit compatibility decision. Do not harvest every handoff or report on start.
3. **Expose the same small tool description automatically and on demand.** Replace the
   current preamble with a shared emitter. Candidate new entry: `doc-slicer --tools`, which
   emits only that description and resolved locations. Keep header/spec queries free of it.
   The name is proposed, not implemented. If another CLI mode feels excessive, ship A and
   keep the description in the existing preamble until real dispatch use justifies the mode.
4. **Make delegation explicit.** The controller passes a concrete handoff, target checkout
   and base, accessible runtime path, required references, and expected report path. Use
   resolved paths valid on the recipient's machine; do not copy this machine's cache path
   into a cross-machine brief. A shared filesystem allows file references; otherwise transfer
   the needed files or concise content before dispatch. A path alone cannot supply missing data.

Choose commit policy for work state deliberately. For loom's cross-machine workflow, recommend
committing selected handoffs and reports. Another repo may ignore scratch state, but then use
direct file reads; do not claim the current discovery-based slicer can retrieve ignored files.
Changing discovery to bypass gitignore would be a separate design decision.

### Candidate literal preamble

Rendered example for this installation after the proposed data-plane work; default locations
shown here would come from resolved config. This is the complete proposed preamble, before
the independently configured bearings and sections:

```text
Loom tools for this repo; configuration: .loom/loom.toml.
Scripts: /Users/zebulonperrin/.codex/plugins/cache/loom/loom/0.2.0/scripts
Run scripts with bash from the repository root.
doc-scan lists managed docs.
doc-slicer --header "<name>" [path-filter] pulls a section.
doc-slicer --spec <capability> [id|section|ids] pulls a spec block.
doc-linter checks docs; doc-stamp updates frontmatter when requested.
Repo specs: docs/specs/. Work state: .loom/specs/, .loom/plans/, .loom/handoffs/, .loom/reports/.
Handoffs carry task scope; reports carry results and evidence.
When delegating, pass the handoff, runtime path, required references, and report destination.
```

Inputs to that emitter: resolved repository root, runtime directory, parsed location settings,
and shipped defaults. It reads no task prompt, transcript, agent id, branch marker, handoff
body, or report body. The optional orientation additionally reads git history and configured
sections, as today. Merely printing the preamble invokes no skill and executes no skill hook.

Candidate fallback sentence for a dispatch brief or skill that needs this surface:

> If Loom's tool description is absent, run the supplied runtime's `doc-slicer --tools`; pull
> further repository sections only when the assigned task needs them.

This cannot bootstrap an agent that receives neither the description nor the runtime pointer.
For 0.2, the controller supplies that pointer, and an interactive user can invoke warp's
existing orientation fallback. Add a short repo instruction through dress only if real fresh
agent tests show a remaining discovery gap. Avoid a seventh mandatory onboarding skill.

For automatic delivery, propose the description only when `.loom/loom.toml` exists. Keep
explicit slicer behavior outside configured repos available. Decide the absent/invalid-config
behavior before implementation: current no-config and parser-fallback tests promise output,
so a blanket early exit would be a behavior change. Consider a hook-specific guard, not an
implicit change to every query. Leave SubagentStart unregistered initially; explicit dispatch
is the 0.2 baseline, and one missed cold-start use would justify evaluating that hook later.

## Acceptance

These are proposed checks for the agreed implementation, not claims that it already exists:

- You showed the literal opening bytes, fallback sentence, config diff, and input list before
  implementing a new context surface. Target the tool preamble at at most 150 words and
  1,200 UTF-8 bytes; measure configured orientation separately and do not silently truncate it.
- You ran meaningful checks for default/custom work-state locations, explicit kind overrides,
  tracked and ignored handoffs, no-config/invalid-config behavior, and clean query output.
  Existing parser/layout behavior remains consistent across affected capabilities.
- On each installed harness, you recorded startup/resume/compact behavior and one fresh
  delegate with an explicit brief and runtime pointer. Record inherited context versus fresh
  delivery, exact input, received text, script count, output size, and time. Test a fork or
  separate background session if that is the route the operator actually plans to use.
- You tried one small useful delegated task with hooks absent: it found the named context,
  returned evidence to the requested report, and did not need the whole parent conversation.
- You ran `bash tests/run` and it printed `ALL TESTS PASSED`; `bash scripts/doc-linter`
  printed `doc-linter: clean ✓`. Carry existing warnings separately from new findings.
- You reconciled the changed context, control-plane, managed-docs, and hook promises by the
  behavior each owns, and listed every added file with its ongoing job.

Prefer one measured pass per route over a new broad harness matrix. If B grows beyond this
small surface, ship A and use the resulting handoffs to learn what context support is missing.
